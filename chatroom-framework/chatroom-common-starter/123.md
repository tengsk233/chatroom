## 1\. Pain Points

Modern software teams face significant challenges in end-to-end (E2E) test automation. **E2E Automation System 2.0** was conceived to tackle these pain points head-on:

- **Manual E2E Test Development is Slow and Costly:** Converting product specifications into automated tests traditionally requires significant manual effort (often multiple days per feature). This delays feedback; for example, a QA engineer might spend 2-3 days writing and updating tests for a complex feature, slowing down release cycles.
- **Fragile Tests and Frequent Failures:** Without intelligent handling, E2E tests often break due to minor UI changes or timing issues, leading to flakiness (we observed ~10-15% of test runs failing spuriously in the old setup). Engineers waste hours investigating false failures or rerunning tests, reducing confidence in the test suite.
- **Slow Bug-Fix Feedback Loop:** When a test finds a real bug, logging it, getting it fixed by developers, and verifying the fix can span days. Meanwhile, the failing test keeps blocking the pipeline. There's also a risk of duplicate bug reports if the same failure is logged repeatedly on each run (we've seen multiple redundant tickets for a single root cause in manual workflows).
- **Limited Scalability of Test Execution:** Running tests sequentially becomes a bottleneck as the test suite grows; a full run can take hours, delaying feedback on new commits. Traditional setups often lack easy ways to parallelize test execution and coordinate results, meaning slower feedback for large suites and overburdened CI pipelines.
- **Testing-Development Integration Gap:** Traditional automation stops at detecting failures. It doesn't assist in diagnosing or fixing issues in the application. QA engineers must hand off failure details to developers and manually retest after fixes, missing opportunities to leverage automation for debugging and thereby prolonging the resolution of issues.

By addressing these pain points, **E2E Automation System 2.0** accelerates the testing process and improves reliability, allowing teams to catch issues faster and deliver with confidence.

## 2\. Key Features

**E2E Automation System 2.0** introduces a suite of innovations and improvements to solve the above challenges. Its key features include:

- **Multi-Agent Orchestration:** A coordinated **5-agent architecture** that automates the entire testing lifecycle.
- Agents have specialized roles: **Test-Design** (parses specs and generates test cases), **Test-Creator** (writes & runs Playwright test scripts), **Frontend Bug-Fixer** (diagnoses & fixes front-end issues), **Test-Validator** (compares outcomes against expected results), and a central **Master Orchestrator** that manages them.
- The orchestrator schedules tasks and ensures agents work in concert, handing off tasks (e.g., from test execution to bug fix) seamlessly. This parallel division of labor reduces manual intervention and enables concurrency in test pipelines.
- **Performance Optimizations (3× Faster):** Significant speed-ups in test execution and agent response.
- **Timeout reduction:** Test step timeouts were cut from 180s to 60s, eliminating unnecessary waiting. Page interactions (load, clicks, script eval) use tuned timeouts (5-20s) to fail fast on issues yet allow realistic page load times.
- **Faster initialization:** Pre-initializing code intelligence and browser automation sessions prevents slow start-ups. As a result, average end-to-end test duration dropped from ~15 minutes to ~5 minutes, a 3× improvement.
- **Real Browser Verification (Integrated Chrome DevTools):** The Test-Creator agent **mandatorily uses a live Chrome browser** (via Chrome DevTools Protocol) to validate selectors and actions before and during test execution.
- Every critical step (page loads, clicks) is first attempted in a real browser environment. This catches issues like incorrect selectors or hidden elements _before_ the test script runs, reducing flakiness.
- The agent can retrieve actual DOM states, detect duplicated or missing elements, and capture screenshots at each step. In fact, using this feature the system discovered real front-end bugs during test development, proving its value in early bug detection.
- **Intelligent Error Diagnosis:** When a test fails, the system doesn't simply retry blindly. It applies **AI-driven classification** to pinpoint the failure type and decide next steps (boosting debugging efficiency by an estimated 5-7×):
- _Type A - Wrong URL or Config:_ Immediately correct obvious mistakes (e.g., using a wrong base URL) and rerun the test without manual intervention.
- _Type B - Test Script Issue:_ If a locator or test logic is wrong, the agent adjusts the script (such as fixing a selector) instead of rerunning the same failing code.
- _Type C - Transient Fluke:_ Intermittent issues (timeouts, network glitches) trigger a limited **smart retry** (usually 1-2 retries) rather than failing outright, avoiding random noise.
- _Type D - Frontend Bug:_ If the failure appears due to a web application bug (e.g., a JavaScript exception, UI element truly not updating), the system creates a **bug task** for a fix and **blocks the test** until it's resolved (no pointless re-runs).
- _Type E - Backend/Environment Issue:_ Issues outside the front-end (server errors, environment down) result in the test being halted and marked, so it doesn't keep re-running a failing scenario it cannot fix.
- **Closed-Loop Bug Resolution Workflow:** The system tightly integrates test failure and bug fixing into one workflow, ensuring no test stays broken due to an application bug:
- **Auto Bug Reporting:** For Type D failures, the Test-Creator agent automatically creates a detailed bug ticket. The description includes the test case, steps to reproduce (user actions), expected vs actual outcomes, plus evidence (screenshots of the UI, console logs, and even relevant snippet of code or network call if available).
- **Auto Assignment & Dependency:** The bug ticket is linked to (and blocks) the failing test task in the queue. This prevents an _infinite loop_ where a failing test keeps creating new bugs on each run - a critical improvement over naive automation.
- **Automated Bug Fixing:** The **Frontend Bug-Fixer agent** picks up the bug task, uses code intelligence and debugging tools to identify the root cause, and even applies a code fix if feasible. It updates the bug ticket with analysis and changes made (or recommendations if it's not a direct code fix).
- **Test Re-run:** Once fixed, the bug is closed by the agent and the orchestrator automatically reopens the blocked test task. The Test-Creator agent then reruns the test to verify the fix. The result: a bug identified by a test gets fixed and validated in a single continuous cycle without waiting for human intervention.
- **Robust Navigation Rules:** All test scripts strictly follow **Navigation Rule #12** - _simulate user navigation, never jump directly via URL after the initial page load_.
- The Test-Creator agent uses page.goto() **only** for the app's entry point (e.g., the main dashboard). All subsequent navigation (opening a detail page, clicking "Edit", etc.) is done via real user interactions (page.click() on links/buttons, form submissions, etc.).
- This approach ensures that all intermediate UI logic (event handlers, page transitions, authentication checks) execute just as they would for a user. It prevents tests from bypassing crucial steps that could hide bugs. For example, in one case the agent detected that a direct URL access skipped a necessary initialization step - something a user would have triggered by clicking through the UI.
- By enforcing this rule at multiple levels (agent prompt, config, and SOPs), the system improves test reliability and fidelity to user experience.
- **Stability and Safety Enhancements:** Many subtle improvements make the automation process more robust and safe to run unattended:
- **Agent Auto-Exit:** Agents are launched with a --no-interactive flag, ensuring they don't enter a REPL or wait for user input after completing tasks. They cleanly exit, allowing the orchestrator to continue automatically. This prevents "stuck" agent processes and requires no manual supervision.
- **Safe Task Command Execution:** All interactions with the task tracker (Beads bd CLI commands) are executed in the correct project context. The agent workflows explicitly cd to the project directory before running any bd command, avoiding errors like "not in a git repository" which happened in earlier iterations.
- **Preemptive Resource Cleanup:** The Chrome DevTools automation opens real browser pages for testing; the agent always closes pages after use to free memory and ensure a fresh state for the next test. This avoids cross-test interference and browser bloat during long runs.
- **Retry with Caution:** Where retries are used (e.g., DevTools actions), they are limited (up to 3 attempts) and logged. There is no infinite retry; the system either resolves the issue or fails fast with diagnostic info, making it easier to pinpoint problems without endless loops.

Each of these features works in synergy within the E2E Automation System, transforming end-to-end testing into a faster, smarter, and more autonomous process.

## 4\. System Architecture

\- A **Master Orchestrator** (Python daemon) that governs the workflow.

\- Multiple **AI Worker Agents** (running via kiro-cli) that perform the actual work on each task, according to pre-defined workflows (SOPs/skills).

### Component Descriptions

- **Master Orchestrator:** A Python 3 daemon process (master_orchestrator_enhanced.py) that is the brain of the system. It continuously loops to check for tasks that are ready to run. Depending on the task type (design, test, bug, etc.), it launches the corresponding agent with a context-specific prompt. It also handles concurrency (multiple tasks in parallel if configured), tracks execution time, and updates task status. The orchestrator is resilient - if no tasks are ready, it waits and periodically logs the system status (including any tasks that are blocked waiting for something, to help identify deadlocks).
- **Beads Task Queue:** We use _Beads_ (an internal CLI-based task tracking system) as a lightweight queue and dependency manager. Tasks (like "TC11: Update Carrier Cut-off Time") are created with types (task, bug, design, etc.) and priorities. Dependencies can be set; for example, a Bug task can _block_ a Test task until resolved. The orchestrator queries Beads for tasks that are ready to run (no unresolved dependencies) and those that are blocked. This approach gives us persistence (tasks are saved in a git-tracked YAML store) and flexibility to manage task relationships, essentially acting as the memory of the system.
- **AI Worker Agents:** Each agent is implemented as a conversational AI (via kiro-cli chat) with a specialized prompt and a set of tools/skills. The agent reads the context (provided by the orchestrator prompt, which can include the task description, relevant rules, and even file contents) and then follows a defined procedure (SOP) to complete the task. For instance:
- The **Test-Design Agent** might have a prompt instructing it how to parse a specification document and output test case files. It may use an internal knowledge of documentation format to extract key scenarios and create markdown files for each test case.
- The **Test-Creator Agent** has a prompt loaded with _Critical Rules_ (like the navigation rules and performance guidelines) and uses the chrome-devtools tool to open pages and validate selectors. It then writes a Playwright test script (in TypeScript) step-by-step, executes it, and captures results. If errors occur, it refers to error-handling logic (possibly loaded via an automation skill) to decide whether to retry, fix, or escalate to a bug.
- The **Frontend Bug-Fixer Agent** is provided with the context of a bug (including the detailed description from the bug ticket). It automatically initializes the code intelligence for the relevant repository and performs tasks like searching the codebase for error patterns, diagnosing the root cause, and even making code changes (for certain types of issues like a missing null check or a typo). It then documents what it did in the bug ticket and closes it if fixed. Notably, it always reopens the blocked test to ensure the validation loop closes.
- The **Test-Validator Agent** (optional step) takes the outputs of a test (screenshots, logs, data) and compares them against expected results or reference materials (for example, comparing a UI screenshot to a baseline image, or verifying that a setting saved via UI actually reflects in the database/API response). It helps double-check that a "passed" test indeed met all acceptance criteria, catching any discrepancies that might be missed (like a visual glitch).
- **Integrated Tools:** Agents aren't working blindly; they leverage powerful tools to interact with the system and code:
- _Chrome DevTools MCP:_ A multi-channel provider (MCP) that lets the agent control Chrome. The agent can open pages, click elements, run JavaScript in the context of the page, and capture screenshots - all by issuing high-level commands. This is crucial for bridging between the AI agent's planning and the actual web application UI.
- _Workspace Search MCP:_ Allows semantic or regex searching through the project's codebase (like a supercharged grep). Agents use this to quickly locate code relevant to the test or bug - e.g., finding the component responsible for a certain UI or retrieving the implementation of a function that a test is failing on.
- _Code Intelligence:_ Essentially an in-process language server for the codebase, giving the agent capabilities like "find all references of this function" or "open this file and list diagnostics." The orchestrator pre-loads this to avoid slow startup. This tool turns the agent into something of a developer assistant, enabling it to understand and even modify code when fixing bugs.
- _Beads CLI:_ Provides the interface for the agent to report back to the task system - for example, creating a new task (bd create), adding a dependency (bd dep add to link a bug to a test), updating status (bd update ... --status in_progress/blocked/closed), and syncing tasks to persistence (bd sync). Agents use these commands as actions during their workflows.

### Data Flow & Sequence

To illustrate how these pieces work together, consider a typical sequence when running a new feature through this system:

- **Test Design Phase:** A QA lead creates a "design" task in Beads with a link to the feature's specification (for example, a Quip document URL) and a feature identifier. The orchestrator picks up this task and launches the **Test-Design Agent**. The agent fetches the spec content (perhaps via an API or an export), then goes through its 7-phase workflow: it analyzes the spec, extracts any images or UI references, identifies test scenarios, produces an execution plan, then writes out individual test case files (e.g., TC10-FeatureX-ScenarioY.md) and updates an index. Once done, it marks the design task as completed. The output artifacts (test case markdown files and reference images) are now part of the project docs.
- **Test Creation & Execution Phase:** The orchestrator now sees multiple new "test case" tasks (TC10, TC11, etc.) created by the design agent. It starts with the highest priority one, launching the **Test-Creator Agent** for, say, TC10. The agent reads the test case description (goal, steps, expected results) from the file generated earlier. It also may consult the codebase (using Workspace Search) to understand the UI elements or API involved. Then it performs the critical **DevTools verification**: opening the target application page in Chrome, navigating via clicks as the test scenario requires, and ensuring all selectors and expected elements are present. It might take screenshots for reference. After this dry run, it proceeds to write the actual Playwright test code following proven patterns (login via fixtures, use page.goto for the base URL, then page.click through the flow, taking screenshots at each step for later analysis). The agent executes the test script. If the test passes (no assertions fail and no errors), it closes the task as completed. If it fails, the agent immediately enters debug mode: checking the error message, analyzing screenshots and console logs, and referencing common failure patterns. According to the failure type, it may fix the test script (and retry), or determine that it's a genuine application bug. In the bug case, it creates a new Bug task in Beads, attaches it as a blocker to the test task, and marks the test task as "blocked". The orchestrator sees the test task is now waiting on something and will not consider it ready until that dependency is resolved.
- **Bug Fix Phase:** The newly created Bug task (say "Bug: Dropdown value not persisting") is picked up by the orchestrator, which launches the **Frontend Bug-Fixer Agent**. This agent is primed with the bug description (which includes the test context and evidence). It likely uses Chrome DevTools to reproduce the scenario (opening the page and maybe simulating the failing user action to see it firsthand). It then uses Code Intelligence to dive into the relevant front-end code: it might search for the component or function by name, open the source file, and look for obvious issues (like state not updated, missing conditions, etc.). Based on what it finds, the agent either applies a fix (e.g., adding a missing null check, adjusting a conditional, or updating a default value) or determines it's not actually a front-end bug (perhaps the test was doing something wrong or it's a backend issue). In our example, if it finds that the dropdown selection wasn't saved because the test bypassed the UI, it classifies it as a "Test Issue" rather than a product bug. The agent then updates the bug task's description with a clear **analysis result** section, including the classification (bug vs test issue vs env issue), root cause, what was changed (if a fix was made, including file names and line numbers), or recommendations for the test in case it's not a product bug. It then closes the bug task with an appropriate resolution reason (e.g., "Fixed in code", "Not a bug - test adjusted"). Importantly, if it fixed something in code, that change is now in the codebase (committed by the agent or ready for commit).
- **Re-run and Validation Phase:** With the bug task closed, the orchestrator reactivates the originally blocked test task (TC11 in our example). It sets it back to "ready". On the next cycle, the Test-Creator agent will pick up TC11 again. Now, depending on what the bug-fixer did, the test might pass: if code was fixed, the application behavior is corrected; if it was a test issue, the agent will incorporate the bug-fixer's recommendation (e.g., use a different method to select the dropdown) and then run it. Either way, TC11 is executed again. If it passes this time, great - the agent closes it. If it fails differently, the cycle repeats (the system will again diagnose whether it's a new bug or another adjustment needed). In practice, this closed-loop often resolves the issue in one iteration. Finally, the **Test-Validator Agent** can optionally run to compare screenshots or outcomes against the expected baseline for an extra level of verification.
- **Completion:** The orchestrator continues this process for all test tasks. Once all tasks (design, tests, bug fixes, validation) are completed or closed, the feature's test automation is done. The orchestrator can then idle until new tasks are added (or shut down by an operator). Throughout the run, the system logs metrics for each task (start time, end time, success/failure) which can be reviewed later for performance analysis.

This architecture ensures that the system is **extensible** (new agents or tools can be integrated with minimal changes), **fault-tolerant** (one failing task doesn't crash the system; it's isolated and can be retried or fixed independently), and **scalable** (multiple orchestrator threads or even distributed orchestrators could handle large task volumes, and agent logic can be improved over time by updating prompts/skills).

## 5\. Use Cases

Real-world usage of **E2E Automation System 2.0** has demonstrated its effectiveness. Below are several scenarios that showcase how the system operates and the value it provides:

### Case 1: End-to-End Test Automation for a New Feature

**Background:** Our team introduced a complex new feature, _"Location-Level Fulfillment Settings"_, requiring thorough end-to-end testing. Traditionally, QA would manually write test scripts from a requirements doc, a process taking days and prone to missing edge cases. We wanted to accelerate this and ensure full coverage.

**Solution:** Using the E2E Automation System, we triggered an automated test design and execution workflow:  
\- We created a **Test Design** task pointing to the feature's specification (a Quip document). The Test-Design agent parsed this spec, extracting 9 reference screenshots and identifying 6 key test scenarios (covering normal flows and edge cases). It generated 6 test case files (TC10 through TC15) within a few minutes, complete with step-by-step test plans and expected outcomes.  
\- The orchestrator then automatically spawned **Test-Creator agents** for each test case in sequence. For example, **TC10: "View Location-Level Settings"** was executed first. The agent opened the web app at the main Locations page, clicked through the UI (selecting a specific location, then navigating to the Fulfillment Settings section), and verified that the settings page loaded correctly with all expected elements. The test ran successfully on the first try and was marked passed. Screenshots from each step (homepage, after clicking location, after opening settings) were saved for documentation.  
\- Next, **TC11: "Update Carrier Cut-off Time"** ran. During execution, the agent clicked on a dropdown to change a carrier cut-off time and submitted the form. However, the test assertion noticed that the updated value did not persist (the old value was still shown after refresh). The agent gathered a screenshot of the result and the console log which showed a JavaScript error. It diagnosed this as a likely **frontend bug** (since the UI didn't behave as expected despite correct test steps). The Test-Creator agent automatically **created a Bug task**: "Bug: Dropdown value not persisting in OFS", including details: the user action (selecting a time and saving), expected outcome (new time should be saved), actual outcome (old time remained), and evidence (screenshot showing the unchanged value, plus the console error text). It also smartly marked the test TC11 as **blocked** by this bug, avoiding further futile re-runs.  
\- The **Frontend Bug-Fixer agent** took over the bug task. By inspecting the console error and using code intelligence, it found that the issue was actually with the test script's approach: the test had used a low-level command to set the dropdown value (bypassing React's state management) instead of simulating a user selection. Essentially, this was a **Test Issue** - the application itself was fine, but the test methodology was flawed. The agent updated the bug ticket to note this classification and provided a solution: use the proper Playwright dropdown selection (e.g., click the dropdown and press the arrow keys or select an option by text). It did not make any code changes (since the app code was not at fault) but did suggest how to fix the test. The bug was then closed as "Not a product bug - test adjusted". Importantly, the agent then **reopened the TC11 test task** for another run.  
\- The orchestrator, seeing TC11 is ready again, launched the **Test-Creator agent** for TC11 one more time. This time, the agent incorporated the fix: it interacted with the dropdown using a proper user simulation. After making this change, the agent re-executed the test steps. The form submission succeeded, the new cut-off time was saved, and the test passed. TC11 was closed as successful.  
\- The remaining test cases (TC12-TC15) proceeded similarly. Some covered edge cases like invalid inputs or toggling certain settings. Thanks to the robust navigation and error handling in place, all these tests passed on either the first run or after minor automatic adjustments.

**Result:** Within about **one hour**, the system autonomously delivered a full suite of 6 end-to-end tests for the new feature and even handled a tricky scenario that revealed a test design flaw. This saved our QA team an immense amount of time - what traditionally might have been 3-4 days of work (writing scripts, running them, debugging issues, communicating with developers) was accomplished with minimal human intervention. Moreover, the tests are now part of our regression suite, continuously guarding that feature.

**Evidence:** After the run, the **Playwright test report** showed all tests passing. The bug ticket created (#OFS-123, for example) was updated by the system with a detailed analysis and then closed - one can see the comments added by the "Frontend Bug-Fixer" agent identifying the root cause. The task-execution-report.json logged by the orchestrator also confirms the timeline: TC10 completed in ~7 minutes, TC11 took two attempts with an intermediate bug fix (total ~10 minutes), and all tests completed successfully. Screenshots for each step of each test case were saved in the repository (docs/Pages/frontend-pages/feature-abc/…) for future reference, which also help in creating user documentation or troubleshooting guides.

### Case 2: **Automated Bug Detection and Resolution** (Closed-Loop Bug Fix)

**Background:** In a regression run for an existing feature, one test began consistently failing when selecting a pickup time slot on an order fulfillment page. Normally, a failing regression test would alert QA, who would then file a bug, and developers might take a day or more to investigate the root cause. We wanted to see how the system's bug-fixing loop handled a real application bug.

**Solution:** Once the failing test was detected by the **Test-Creator agent** (it threw a JavaScript TypeError in the console and an assertion failed), the system did the following:  
\- **Auto Bug Filing:** The agent created a **Bug task** immediately. For example, it logged "Bug: Pickup time selection not saved on Order Fulfillment" with a priority flag. The description included the test name, exact user steps (e.g., "Select '10:00 AM' from pickup time dropdown and click Save"), the expected result ("Pickup time should update to 10:00 AM for the order"), and actual result ("Time remained as 9:00 AM; console showed TypeError on save"). It attached the screenshot of the page after saving (which clearly still showed 9:00 AM) and noted the console error message about an undefined value.  
\- **Automated Diagnosis:** The **Frontend Bug-Fixer agent** picked up this bug task. Using the description, it launched the web page through Chrome DevTools and reproduced the steps (selecting 10:00 AM and saving). It observed the same error in the console. Next, it ran a code search (via Code Intelligence) for the function or component handling the save action. It found the relevant React component (OrderFulfillmentSettings.tsx) and noticed a piece of code where it tried to read pickupTime from the form state without a proper null check. Indeed, if that field was not set for some reason, it could cause a TypeError. This matched the symptom. The agent proceeded to **edit the code**: it added a conditional check to ensure pickupTime existed before using it (preventing the TypeError). It then tested the change by reloading the page in Chrome DevTools and re-running the save action - this time no error occurred and the new time saved correctly.  
\- **Bug Ticket Update:** The agent updated the bug's description with an analysis section: it marked it as a **FRONTEND_BUG** (a real code issue in the application), detailed the root cause ("Missing null check on pickupTime caused a TypeError, preventing save"), and documented the fix ("Added if (!pickupTime) return defaultValue; at line 123 of OrderFulfillmentSettings.tsx"). It also listed the file that was changed. The bug status was then set to closed with reason "Fixed in code". The agent also added a note that the test should be run again to verify. Simultaneously, it **reopened the blocked test task** that was waiting on this bug.  
\- **Verification:** The orchestrator relaunched the **Test-Creator agent** for the affected test case. The test ran through the same steps - this time, because the code was fixed, the pickup time updated as expected. The test passed, confirming the bug was truly resolved. The Test-Validator agent did a quick check comparing the UI to the expected state and found everything in order.

**Result:** The entire find-fix-verify cycle was completed in roughly **15 minutes** without human intervention. In a conventional setup, discovering the cause of the bug could have taken a developer a few hours (digging through logs, reproducing in a dev environment), plus the coordination overhead of filing and triaging the bug. Here, the system proactively pinpointed the issue and even applied the code fix. This dramatically shortened the bug's lifetime and reduced the manual work to essentially **zero** (developers later reviewed the automated fix, but it was correct and required no changes).

**Evidence:** The git repository shows a commit from the automated agent at the timestamp of the fix (with a message referencing the bug ID and the fix). The closed bug ticket contains the analysis written by the agent, which reads almost like a developer's resolution notes. The final test run report shows all tests passing. This case validated that the system can handle not just test problems but real product issues, improving overall product quality faster.

### Case 3: **Parallel Regression Testing with Multiple Agents**

**Background:** Our continuous integration (CI) environment runs dozens of E2E tests for each build. Sequential execution was becoming a bottleneck, so we wanted to utilize the system's concurrent execution ability to speed up regression feedback.

**Solution:** We configured the Master Orchestrator to run in **concurrent mode** with 2 workers (--concurrent 2). Then we triggered a regression run of several test tasks at once. Here's how it played out:  
\- The orchestrator picked up **two test tasks at a time** and launched two **Test-Creator agents** in parallel. For instance, TC10 and TC11 started together. This immediately utilized our multi-core test environment better, as both the browser automation and the AI reasoning for each test ran simultaneously.  
\- In our example, TC10 was a straightforward test and passed. TC11 encountered a failure (same scenario as earlier, a dropdown issue). While TC11's agent was creating a bug task for its failure, the orchestrator already marked TC10 as done and proceeded to start **TC12** with another agent in that freed slot.  
\- Soon we had one agent working on the bug fix task (for TC11's bug) and another agent executing TC12. This overlapping execution meant the bug was being analyzed while later tests were already running, reducing idle time.  
\- Once the bug fix was done and TC11 was reopened, it was picked up again promptly while other tests (TC13, TC14, etc.) continued, still with at most two running at any given time. The orchestrator managed the pool of tasks efficiently: whenever a slot freed (a task finished), it pulled the next ready task (prioritizing any reopened tasks like TC11 to verify the fix).  
\- With 2 parallel workers, we observed that the overall suite (5 test cases + 1 bug fix in this run) finished about **30% faster** than it would have serially. We also tested with --concurrent 3 and saw even further reduction in total time, though we had to ensure our test environment could handle 3 browsers running at once.

**Result:** The concurrent execution capability proved valuable for scaling. The CI pipeline's E2E test stage was shortened from ~40 minutes to ~28 minutes with two agents (and could be near ~20 minutes with three agents, given enough resources). The orchestrator ensured results remained consistent - it handled synchronization (no two agents worked on the same task or bug simultaneously) and maintained the integrity of the workflow even in parallel mode.

**Evidence:** We gathered orchestrator logs from the concurrent run showing interleaved execution: e.g., at one timestamp, TC11's agent logging a bug creation while at the same time TC12's agent logs a successful step. The task-execution-report.json recorded the individual durations and confirms multiple tasks overlapping in time. The final metrics showed all tests passed and one bug fixed, with timestamps indicating concurrency. This use case demonstrated that the system can effectively scale horizontally to handle larger test suites within practical build times.

## 7\. Troubleshooting

Even with a robust system, you might encounter issues during setup or execution. Here are common problems and their solutions, distilled from our experience:

**Issue 1: Agent Process Doesn't Terminate (Stuck in Interactive Mode)**  
\- **Symptoms:** You see in the orchestrator log that an agent reached 100% or finished its output, but the orchestrator is not moving on. The agent might appear to be waiting for input (e.g., a > prompt).  
\- **Cause:** The agent was launched without the --no-interactive flag, causing it to drop into an interactive shell after completing its main task. This can happen if the orchestrator's command is misconfigured.  
\- **Solution:** Ensure the orchestrator uses the correct flags. In master_orchestrator_enhanced.py, when it calls kiro-cli chat, it should include --no-interactive. In our provided orchestrator code, this is already set for all agents. If you wrote a custom integration, double-check that. Once fixed, the agent will exit on its own when done. If an agent ever does hang, you can manually terminate it (find the kiro-cli process and kill it), then correct the config and rerun.

**Issue 2: "Code Intelligence" Initialization Hangs**  
\- **Symptoms:** When a bug task starts, the orchestrator logs something like "Initializing Code Intelligence in FBMS…" and then waits indefinitely (or at least far longer than expected). The bug-fixer agent doesn't proceed.  
\- **Cause:** The code intelligence tool (LSP server) is taking too long to start or is waiting for input. In earlier versions, we saw that calling kiro-cli chat "/code init" could hang if not run in non-interactive mode or without a timeout.  
\- **Solution:** We updated the orchestrator to run the init command with --no-interactive and a 30-second timeout. If you face this, make sure your orchestrator's code intelligence init step looks like:  

init_cmd = f'cd {project_path} && kiro-cli chat --no-interactive --trust-all-tools "/code init"'  
subprocess.run(init_cmd, shell=True, timeout=30)

This ensures it won't hang more than 30s. If the issue persists (e.g., for a very large repository indexing might need more time), you can extend the timeout slightly or run the init manually beforehand. Also verify project_path is correct so it indexes the right codebase.

**Issue 3: Chrome DevTools MCP Not Available**  
\- **Symptoms:** The Test-Creator agent immediately fails at Step 6 (the Chrome DevTools step) with errors like _"Tool validation failed: No tool with alias 'chrome-devtools'"_ or it times out trying to open a page.  
\- **Causes:** Either Chrome isn't running in debug mode on the expected port, or the agent's MCP configuration is missing/incorrect.  
\- **Solution:** 1. **Start Chrome** - Ensure you have Chrome running with --remote-debugging-port=9222 **before** starting the test. If you forget, the agent can't connect to the browser. Start it and retry.  
2\. **Check MCP Config** - Open config/.kiro/agents/test-creator.json (or the agent config you use) and verify the mcpServers section. It should contain something like:  

"mcpServers": {  
"chrome-devtools": {  
"command": "npx",  
"args": \[  
"-y", "chrome-devtools-mcp@latest",  
"--browser-url=<http://127.0.0.1:9222>"  
\]  
}  
}

This tells the agent how to connect to the Chrome DevTools MCP. The URL must match the port Chrome is using. If you use a different port, update it here. If your environment requires a specific version of the MCP npm package, adjust accordingly.  
3\. **Network Conflicts** - Occasionally, if port 9222 is in use or blocked, you can try a different port (say 9223) for Chrome and update the config to that. Also, ensure no firewall is blocking localhost access.

- **Symptoms (alternate):** The agent appears to connect to Chrome but actions (like new_page or click) time out.
- **Solution:** This could be due to the page taking too long to load or an invalid URL. Check that the base URL the test is using is correct and the web app is running at that address. The logs might show what URL it tried to open. If it's wrong (like pointing to production instead of local), fix the test case or base URL configuration (the agent's prompt may allow specifying base URL). We enforce using a local integration URL in our prompts to avoid this.

**Issue 4: Infinite Loop of Bug Creation**  
\- **Symptoms:** A test fails and files a Bug task. You fix the bug, rerun the test, but it fails again (perhaps due to the same bug or not picking up the fix), and the agent files yet another Bug task for the same issue. This can repeat, cluttering the task queue with duplicates.  
\- **Cause:** The agent isn't checking for an existing open bug and keeps creating new ones for each run. This was a known pitfall in early versions if Step 9a (dependency check) wasn't implemented correctly.  
\- **Solution:** The fix is twofold - ensure the agent workflow includes a check for existing bug dependencies, and improve the test or bug fix so it doesn't repeat fail. In **v2.0**, we added a **Critical Rule** that before creating a new bug, the Test-Creator agent must inspect the current test task's dependencies (via bd show) to see if a similar bug is already linked. If yes, it should not create a duplicate and instead just log that it's still blocked by the known bug. Verify that your agent's instructions (prompt or skill file) contains this logic. If using our config, look for a step described as "Step 9a: Check existing Bugs" - it should be present. If you accidentally removed or modified it, reintroduce that logic.  
Additionally, if this loop is happening because the bug fix didn't actually resolve the issue (so the test keeps failing), investigate the bug resolution: maybe the fix was incomplete. The good news is the system will typically only create one bug; subsequent failures remain linked to that bug. You may just need to reopen that bug and address the additional root cause.

**Issue 5: Beads Commands Fail (Not in Repo)**  
\- **Symptoms:** Agents attempt to update or close tasks but you see errors like _"fatal: not a git repository"_ or _"bd: no task found"_. Or nothing happens when a task should be closed.  
\- **Cause:** The bd CLI likely ran in the wrong working directory, so it didn't know about the task repository. For example, if an agent process starts in a temp directory or some directory without the .beads/ folder, bd commands won't target the right project.  
\- **Solution:** Always ensure bd commands execute in the project's root (where the .beads directory resides). Our agent prompts prefix every bd command with cd /path/to/project. Check the agent configurations for any bd update, bd close, etc., and confirm they do a cd to the correct directory first. If you changed the project path or are running on a different machine, update that path in the prompt. For example, if your project is in /home/user/E2E-Automation, use that in the prompt instead of our Mac-specific path. After making these changes, sync the config and try again.

**Issue 6: Tests Use page.goto() Instead of UI Actions**  
\- **Symptoms:** Some tests navigate directly to sub-pages (e.g., an edit page) using page.goto('.../edit') after already being on a page, rather than clicking links or buttons. This might cause missing data or state in the UI, leading to false failures or not truly testing what a user does. You might notice tests passing but not actually exercising all functionality.  
\- **Cause:** Not following Navigation Rule #12 - tests were written (perhaps by earlier practices or other team members) to shortcut navigation for speed, but this bypasses client-side logic.  
\- **Solution:** Adhere to the navigation best practice: **only use page.goto() for the initial page load of your application**, and **use UI interactions for everything after**. For any test scripts that violate this, refactor them. Example fix:  

// Instead of jumping directly to an edit page:  
// await page.goto('<https://app/locations/123/edit>'); (BAD)  
<br/>// Do this:  
await page.goto('<https://app/locations>'); // go to main page  
await page.click('text=Location 123'); // click the specific location  
await page.click('text=Edit'); // then click edit on that page  
// now do edit actions...

This ensures the test goes through the same clicks a user would. Our Test-Creator agent automatically enforces this pattern when generating new tests, but it's something to watch out for in any manually written or legacy tests added to the suite.

**Issue 7: Custom Skills/SOP Changes Not Reflected**  
\- **Symptoms:** You modified a skill (SOP) file to adjust the agent's behavior, but when running the system, the agent doesn't seem to follow the new instructions. It behaves as if the old skill/prompt is still in use.  
\- **Cause:** Two possibilities: the skill isn't being loaded by the agent, or the skill file changes weren't picked up. If the agent config doesn't include a hook to load your skill, it won't use it. Or if you updated the wrong file (e.g., edited config/.kiro/sops/... but the agent is using an outdated skills/.../SKILL.md), your changes won't apply.  
\- **Solution:** 1. **Ensure skill injection:** Check the agent's config JSON for a hooks section. For example, Test-Creator has:  

"hooks": {  
"agentSpawn": \[  
{ "command": "aim skills inject --include-skills 'e2e-test-automation'" }  
\]  
}

This means when the agent starts, it loads the e2e-test-automation skill. If you created a new skill or renamed something, update this accordingly.  
2\. **Sync SOP to Skill:** If you edited config/.kiro/sops/e2e-test-automation.sop.md, you should copy that content into skills/e2e-test-automation/SKILL.md (the agent actually reads the latter at runtime). We maintain the SOPs in the config directory for version control, but the live agent uses the compiled skills directory. After copying, restart the orchestrator.  
3\. **Verify load:** Run aim skills list in the context of the agent (if possible) or look for log lines that indicate the skill content was loaded. If an agent doesn't list the skill, it didn't load it. You can also deliberately have the agent output something from the skill (like a phrase in the skill's preface) to confirm.

If none of these address your issue, consider examining the orchestrator log for any unhandled exceptions or stack traces, and enable more verbose logging on agents. Given the complexity of the system, most issues boil down to configuration mismatches (paths, ports) or not following the intended setup steps. Once configured correctly, the system is quite self-sufficient.

## 8\. Best Practices

To get the most out of **E2E Automation System 2.0**, keep in mind the following best practices. These are derived from lessons learned during development and deployment of the system:

**1\. Use Clear and Consistent Task Naming:**  
When creating tasks (especially manually, or when naming test cases in design specs), use a concise but descriptive format. Include an identifier (like "TC10") and a short description of the test or bug. For example:  
\- ✅ _"TC10: View Location-Level Settings (OFS)"_ - instantly tells what's being tested.  
\- ✅ _"Bug: \[Feature\] - Dropdown value not persisting"_ - clearly indicates the area and nature of the bug.  
Avoid vague titles like "Test1" or "Some bug", which make tracking and triaging harder. Good naming conventions improve collaboration and traceability, especially when reviewing logs or task lists.

**2\. Write Detailed Bug Reports (for Agent and Human Benefit):**  
Our system auto-generates bug descriptions, but if you ever manually file a bug or want to enrich the info, include:  
\- **Test Case and Context:** Reference the test scenario or user story that discovered the bug.  
\- **Steps to Reproduce (User Actions):** Bullet out exactly what was done. Even though the test script is available, having a narrative helps developers and the bug-fixer agent.  
\- **Expected vs Actual Behavior:** Clearly state what should have happened versus what did happen. This frames the problem.  
\- **Evidence:** Attach screenshots (showing the state of the UI), console logs or error messages, and any relevant data (e.g., API response if known). The more evidence, the easier the diagnosis.  
\- **Suspected Components:** If you have a hunch of which part of the system is faulty (frontend, backend, specific module), note it. The agent uses this as a clue to focus the search.  
A well-documented bug can be resolved by the agent faster (or by a developer if it gets handed off). It also avoids back-and-forth communications.

**3\. Mimic Real User Flows in Tests:**  
Always design tests to follow actual user interactions. This ensures that your tests catch issues a real user would face and remain resilient to UI changes that still preserve user experience. Concretely:  
\- Do the entire login and navigation steps as a user would (our framework provides an extension-fixtures login for speed, but from there, navigate by clicking links, buttons, etc.).  
\- Avoid direct DOM manipulation or script injection in tests except for reading values or in truly unavoidable cases. If you find yourself writing page.evaluate(() => {...}) to force some state, consider that a red flag; try to find a way to do it via the UI (or question if the test is covering the right thing).  
\- Include assertions that mirror user expectations, not just internal states. For example, instead of checking a hidden form field's value, verify what the user sees on the screen or via an official API response.

**4\. Optimize and Calibrate Timeouts:**  
Using the right timeout values is crucial for balancing speed and stability:  
\- **Test Timeout:** 60 seconds has proven sufficient for most page flows in our context. If your app is known to be slower, you can adjust to, say, 90s, but be cautious about creeping up too high. Long timeouts can mask performance issues and slow down feedback.  
\- **Step Timeouts:** We set specific tool timeouts (Chrome DevTools actions) shorter, e.g., 15s for a new page load, 5-10s for element actions, since those either succeed quickly or indicate a problem.  
\- **Implicit Waits:** Use page.waitForLoadState('networkidle') or specific conditions after navigation to ensure the page is fully loaded before interacting. This removes the need for arbitrary sleep delays and makes tests more deterministic.  
\- Regularly review if tests are hitting timeouts. If so, investigate if the timeout is too short or if there's a real issue (like an element taking too long to appear). Adjust accordingly.

**5\. Actively Monitor Test Runs for Flakiness:**  
Even with all safeguards, always keep an eye on test results over time:  
\- Use the built-in metrics and reports. For instance, check the orchestrator's summary after each suite run. If success rate is not 100%, find out why - was it a legitimate bug or a script issue the agents couldn't handle?  
\- Watch for patterns: e.g., if a particular test frequently fails the first time and passes on retry (Type C transient issues), consider building a more robust sync/wait in that test or investigating environmental causes.  
\- Keep the reference images (screenshots) up-to-date. If the UI changes, update the expected screenshots used by Test-Validator or as documentation, to avoid false "differences".

**6\. Sync Configuration Changes to Production:**  
If you experiment with prompt tweaks or SOP changes, remember to propagate them properly:  
\- Edit the files under config/.kiro/ (agents, sops, steering rules) in your source control so changes are tracked.  
\- After testing locally, copy those to the ~/.kiro/ directory (or wherever the live orchestrator reads from). For example:  

cp config/.kiro/agents/test-creator.json ~/.kiro/agents/test-creator.json  
cp config/.kiro/sops/e2e-test-automation.sop.md skills/e2e-test-automation/SKILL.md

\- Then restart the orchestrator to load the new configs.

Maintaining this consistency ensures you're actually running the version of the system you think you are, preventing confusion when debugging issues.

**7\. Keep Chrome DevTools Session Ready:**  
Make it a habit to start Chrome in remote debug mode before kicking off the orchestrator in the morning or as part of your CI job. If Chrome isn't running, the first test will fail and waste time until you realize it. Optionally, you could add a startup check in the orchestrator to warn if it can't reach the Chrome DevTools endpoint.  
\- Always close pages using the close_page tool after each test within the agent workflow. Our system does this to avoid accumulating dozens of open tabs. If you tinker with the agent, ensure you keep that in.  
\- Occasionally, Chrome might crash or get into a funky state (especially if many tests ran). If things start failing unexpectedly at the DevTools step, try restarting Chrome. We found the approach very stable for long runs, but it's good to be aware.

**8\. Prevent Duplicate Bug Efforts:**  
As mentioned, have a clear process to avoid duplicate bug tasks.  
\- If a test fails and a bug is known, link them. Our practice: when a bug is found outside the system (say a manual exploratory test finds a bug), we still create a Bug task in Beads for it and link any affected test tasks to it as blocked. That way, if the automated test hits it, it will see it's already a known issue.  
\- Conversely, if the system created a bug, trust that record. Don't file another for the same problem; instead, use the existing one to track and add info if needed. This leverages the system's closed-loop nature and keeps all info centralized.

**9\. Use Code Intelligence Proactively:**  
For developers or QA using the system, remember you have a powerful ally in the code intelligence integration:  
\- If a test keeps failing, you can manually query the code intelligence via the bug-fixer agent (or a dev-mode agent) to quickly search the code. For example, run an agent with a prompt "Find all references to function X" to get context. This can be faster than IDE searches in some cases because the agent can summarize results.  
\- You might even integrate a "code question" mode where you ask the bot about the code. We've seen value in letting the AI analyze code to suggest why something might be failing. This isn't an official feature, but given the architecture, it's feasible to extend for interactive troubleshooting sessions.

**10\. Continually Refine Tests and Workflows:**  
Finally, treat this system as living - as your application evolves, so should the tests and the agent's knowledge:  
\- Update test cases when requirements change, and rerun the test-design agent for new features or major updates to get fresh coverage.  
\- Expand the common issues knowledge base (COMMON-ISSUES-AND-SOLUTIONS.md) with any new patterns of failures or gotchas you encounter, and ensure the agents are aware of it (e.g., include it in their resources). This way, if a similar issue happens again, the agent might resolve it even faster.  
\- Use metrics to guide improvements: if you notice tests are still slower than desired, maybe there are additional optimizations (like paralleled sub-tasks or caching certain operations) to implement. If a particular agent consumes too much time or memory, profile and optimize its prompt or logic.

By following these best practices, you can maximize the efficiency and reliability of the E2E Automation System, and make it a seamless part of your software delivery process.

## 9\. Future Roadmap

The journey for **E2E Automation System** is ongoing. We have a vision for making it even more powerful and adaptable. Here's what's on the roadmap:

### Short-Term (Next 1-3 Months)

- **Multi-Project & Configurability:** Currently, some paths and assumptions in the agents are specific to our primary project. We plan to externalize configuration such as project paths, base URLs, and repository structure so that the system can be easily pointed at _any_ project. This includes supporting multiple projects concurrently with isolated agent contexts.
- **Enhanced Dashboard/Monitoring:** Introduce a simple web dashboard for real-time monitoring of the orchestrator. This would visualize the task queue, show which agent is working on what, and display metrics (pass/fail counts, durations) live. It will make it easier for teams to observe the automation and intervene if needed.
- **Better Transient Failure Handling:** Although we classify transient issues, we aim to incorporate a smarter way to handle external dependencies (like network calls or third-party services flaking during tests). Possibly by integrating a retry with backoff, or marking such tests to be rerun at the end of the suite if they fail in a suspicious manner.
- **Security and Permissions:** Harden the system for use in more secure environments. This involves isolating agent execution (so a buggy website can't trick the agent into running unintended commands) and adding permission controls if multiple users/teams share an orchestrator.
- **In-Depth Documentation & Tutorials:** While this documentation covers a lot, we plan to create tutorial videos and step-by-step guides, especially for onboarding new team members or open-sourcing the tool internally. A "hello world" example repository with a dummy web app and a few sample tests could help others learn by example.

### Long-Term (6-12 Months)

- **Additional Agent Types:** We envision expanding the system beyond front-end E2E tests:
- An **API Test Agent** could automate testing of backend APIs, generating API calls from a specification (like OpenAPI docs) and validating responses, similar to how Test-Design/Test-Creator work but for services.
- A **Performance Test Agent** might run load tests or measure performance timings for certain flows, then analyze and compare against benchmarks (incorporating performance budgets into automation).
- An **Accessibility Audit Agent** could use tools (like axe-core) to automatically scan pages for accessibility issues as part of each test flow, logging bugs for violations (ensuring accessibility is continuously tested, not just a one-off audit).
- **CI/CD Integration:** Make the orchestrator a first-class citizen in CI/CD systems. This could mean a containerized version of the orchestrator that can be triggered by a CI job, which then returns results in JUnit format or comments on pull requests. We also plan to integrate with issue trackers (like Jira or GitHub issues) for bug tasks, so it can operate outside the local environment easily.
- **Machine Learning & Adaptive Testing:** Investigate using ML to analyze test run data over time. For example, the system could learn which tests are most flaky or which parts of the application are most bug-prone, and prioritize or adjust strategies accordingly. Another idea is **test generation using AI** - feeding the AI more context to suggest new test scenarios that might have been missed (going beyond the initial spec).
- **Remote Execution & Scalability:** As usage grows, we want to support running agents on distributed infrastructure. The orchestrator could dispatch tasks to agent workers on different machines or cloud instances. This would allow scaling to very large test suites or running against multiple browser configurations in parallel (Chrome, Firefox, WebKit, etc., as Playwright supports). A part of this is enabling Chrome DevTools over remote hosts and perhaps using cloud browser services.
- **Plugin Ecosystem:** Open up the system to allow custom plugins or scripts. For instance, a team could write a plugin agent to verify database states after tests, or integrate a custom notification when certain tasks complete. By defining clear extension points (maybe via config or a small SDK), we encourage adoption and tailoring of the tool to various needs.
- **UI for Writing/Editing Tests with AI:** A more exploratory idea is a user-facing interface where a developer or QA can chat with an agent to generate or modify tests on the fly. Think of it as pairing with an AI on test creation: "Show me a test that does X", and the agent writes it, then you say "now add a step to verify Y", etc. This would make test automation more accessible to those less familiar with code, leveraging the same multi-agent intelligence behind the scenes.

**Vision:** Our ultimate goal is to make end-to-end testing a self-maintaining aspect of the development cycle. New feature? Just feed the spec to the system and get a suite of tests. Found a bug? The system not only catches it but fixes it or guides the fix. Flaky test? The system auto-tunes or repairs it. We're moving towards a world where the **E2E Automation System** acts like a smart co-worker in your QA team - tirelessly running tests, learning from them, and improving the product's quality hour by hour. Each roadmap item is a step in that direction, and we're excited to see how far we can go with this approach.

_Empowering teams with reliable, fast, and intelligent test automation - that's the promise of E2E Automation System 2.0. We hope this documentation helps you understand and harness its capabilities._
